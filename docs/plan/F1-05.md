## B. Scope

**In scope:** a central authorization layer per GUIDELINES §6.2 — one guard calling one
`can(principal, action, resource)`; deny-by-default for **authorization** (a route with no explicit
access marker is rejected at runtime **and** fails a boot check and a route-scan test); a code-defined
permission catalog + role→permission map; `docs/security/permission-matrix.md` kept in sync by a test;
stale-role handling (fixing the recorded refresh debt); an ownership/scope scaffold that fails closed
for `CARRIER_ADMIN` until F1-08; a sensitive-action contract (role + reason + fresh roles, audit hook
as a no-op interface); mass-assignment and BFLA tests; explicit classification of every existing
endpoint.

**Out of scope** (the executor must not add these): the audit module and audit tables (F1-06),
idempotency, outbox, carriers tables / `users.carrier_id` / carrier RLS policies (F1-08), any web UI,
any new business endpoint (user management HTTP, base data, announcements…), a `permissions` DB
table, new roles. **No schema change is expected in F1-05.** If a migration or a new business
endpoint becomes necessary, STOP and ask the owner (condition C7).

### B.1 Owner approval conditions (2026-11-21, binding)

- **C1 — Swagger off in production.** `/api/docs` (and its JSON document) must be absent when
  `NODE_ENV=production`. A test boots the app with production config and proves the path is `404`;
  development/test keep Swagger enabled. Registration is extracted into a testable boot helper so
  the test exercises the real code path, not a copy of it.
- **C2 — No existence oracle.** An out-of-scope record answers `404 NOT_FOUND`; an insufficient role
  answers `403 FORBIDDEN`. All `403` bodies are identical to each other, and all `404` bodies are
  identical to each other, regardless of route, role or whether a row exists. Tests prove that an
  existing-but-out-of-scope row and a nonexistent row are indistinguishable, and that a `403`
  never varies with row existence.
- **C3 — Sensitive actions use the intersection.** For a `sensitive` permission the effective role
  set is **token roles ∩ DB roles** (the DB can never add a role the token did not carry). A
  disabled/deleted user or a suspended/deleted tenant is refused (`401` generic) even with an
  unexpired access token.
- **C4 — Lint proof test.** The rule forbidding role checks outside `security/authz/**` must have a
  test proving it fires on a violating controller and passes on a compliant authz-module fixture
  (negative + positive control), like the D11 DB-boundary proof test.
- **C5 — Route-scan negative control.** A throwaway unlabeled controller (test fixture) must make
  the route-scan test fail, and the same fixture must make app startup refuse. Both directions are
  tested, not only the happy path.
- **C6 — Two markers fail.** A route carrying two access markers (for example `@Public()` +
  `@RequirePermission`) is treated exactly like a route with none: boot check refuses, route-scan
  test fails, runtime fails closed. Tested.
- **C7 — Scope freeze.** No new business endpoints and no schema change in F1-05. If either becomes
  necessary, stop and ask the owner before writing it.

## C. Decisions (Z1–Z13)

- **Z1 — Permissions are code, roles are data.** A typed constant catalog
  `apps/api/src/security/authz/permissions.ts` (`resource.action` names, each with a required
  **scope**: `tenant` | `carrier` | `own`, and a `sensitive` flag) and a role→permission map
  `role-permissions.ts`. No `permissions` table: the 3 roles are fixed by the owner, changing who may
  do what is a reviewed code change (with tests), not a runtime setting. This is **not** the BR-12
  queue Policy engine — that stays operator-configurable data (F3). _Rejected:_ DB permission table
  (runtime-editable privilege = new attack surface, no requirement for it); CASL/Casbin libraries
  (heavy for 3 roles; our needs fit ~150 lines of tested code).
- **Z2 — Catalog contents.** Only permissions needed by existing routes and by the next two tasks
  (F1-07 base data, F1-08 carriers) are added to code now; later phases add their own permissions
  together with their endpoints. The matrix doc lists planned later-phase rows in a separate
  "planned, not active" table so the PRD §2 responsibilities stay visible (owner Q2).
- **Z3 — Access markers; exactly one per route.** Every handler carries exactly one of:
  `@Public()` (existing; no principal), `@SelfService()` (any authenticated principal, acts only on
  its own identity — e.g. `/auth/me`), `@RequirePermission(p)` (one catalog permission). None **or
  more than one** (e.g. `@Public()` + `@RequirePermission`) → (a) the app **refuses to start** (boot
  assertion over Nest `DiscoveryService`), (b) the route-scan test fails, (c) at runtime the guard
  answers `403 FORBIDDEN` and logs an error (fail closed even if (a)/(b) were bypassed). A
  throwaway unlabeled controller is the scan test's negative control, and boot refusal is tested
  against the same fixture (owner C5/C6).
- **Z4 — Single authorization guard, fixed order.** New global `AuthorizationGuard` registered
  **after** the existing `AuthGuard` (authentication stays where it is). An anonymous call to a
  protected route → `401`; an authenticated call without the permission → `403 FORBIDDEN` with a
  generic body (never names the missing permission or the required role). All `403` bodies are
  byte-identical, and all `404` bodies are byte-identical (owner C2). A test locks the order. The
  change-password token (audience `bitabar-api:password-change`) never reaches the authz guard as
  a principal.
- **Z5 — `can(principal, action, resource)`** is a pure, synchronous function in
  `security/authz/can.ts`: role→permission lookup, then scope resolution. Unknown roles in a token
  are ignored (never grant). Role-less principals get `@SelfService` only. Controllers never check
  roles themselves — an ESLint rule forbids importing role constants / reading `principal.roles`
  outside `security/authz/**` (same mechanism as the D11 DB-boundary rule, with a proof test).
- **Z6 — Stale roles: hybrid freshness** (owner Q1). Normal permissions trust the verified token
  roles (staleness ≤ access-token TTL, 10 min). Permissions flagged `sensitive` trigger a **fresh
  read** of the user's `status` + roles from the DB inside the guard; the effective role set is the
  **intersection** of token roles and DB roles (a stale grant cannot act; a token cannot gain a role
  it did not carry). A disabled/deleted user **or a suspended/deleted tenant** → `401` generic. Cost:
  one indexed tenant-scoped query (~1 ms) on sensitive actions only — rare operator/carrier actions —
  instead of on every request. Owner C3 makes the intersection and the suspended-tenant case
  mandatory tests.
  _Rejected:_ per-request re-read (adds a DB transaction to **every** authenticated call, including
  driver polling at queue time — the exact load peak F7 benchmarks); token-only (a revoked operator
  could still approve a cancellation for up to 10 min).
- **Z7 — Close the refresh debt.** (a) The refresh path reads `status` + roles **inside the same
  transaction** as the rotation `UPDATE`, so the new token reflects one consistent snapshot. (b)
  Role assignment or revocation through `UsersRepository` revokes **all** sessions of that user in
  the same transaction (owner Q3), so a role change after the snapshot cannot ride a refresh. With
  Z6 the remaining window (non-sensitive, ≤ 10 min) is the accepted A7 TTL risk.
- **Z8 — Scope / ownership scaffold.** The guard resolves a branded `AccessScope`
  `{ tenantId, carrierId?, driverUserId? }` from the principal and stores it in the request's ALS
  context (next to `TenantContext`). Repositories that need scoping accept **only** an
  `AccessScope` (cannot be built from request data — constructor not exported) and must filter
  `tenant_id` **and** `carrier_id` / driver id together with the row id — **never `WHERE id` only**.
  Out-of-scope rows answer `404 NOT_FOUND` (no existence oracle), not 403; an insufficient role is
  `403` and is decided before any row lookup. All `403` bodies are identical to each other and all
  `404` bodies are identical to each other (owner C2). Tests prove an existing out-of-scope row and
  a nonexistent row are indistinguishable.
- **Z9 — Safe interim for `CARRIER_ADMIN`.** Scope resolution for a `carrier`-scoped permission
  needs `carrierId`; the principal has none until F1-08, so resolution **fails closed** (403) — even
  if a carrier permission were mistakenly mapped. In F1-05 the role map gives `CARRIER_ADMIN` **no**
  data permissions at all (self-service only); a test asserts both layers. F1-08 adds
  `users.carrier_id`, a `cid` token claim (or a fresh read), sets `app.carrier_id`, and adds carrier
  RLS policies using `app.current_carrier_id()` — the guard code does not change.
- **Z10 — Sensitive-action contract ("guard ready, audit hook later").** `@RequirePermission(p)`
  where `p.sensitive = true` additionally requires: fresh roles (Z6); a `reason` field in the body
  schema (string, 10–500 chars, trimmed) — enforced by the route-scan test because guards run before
  pipes; and an `AuditHook` interface (`record({actor, action, resource, reason, outcome})`) called
  by an interceptor after the handler. F1-05 ships a **no-op** implementation; F1-06 replaces it.
- **Z11 — Mass assignment.** Every request-body Zod schema is `.strict()` (unknown keys → 400). A
  scan test fails if any body schema contains `role`, `roles`, `tenantId`, `tenant_id`, `carrierId`,
  `carrier_id`, `status`, `userId`, `createdBy` unless the schema is on a written allowlist with a
  reason (empty today). Identity and tenant always come from the principal, never the body.
- **Z12 — Matrix stays in sync.** `docs/security/permission-matrix.md` contains a generated block
  between markers (`<!-- matrix:begin -->…<!-- matrix:end -->`), produced from three inputs (the
  catalog, the role map and the production route scan) by
  `pnpm --filter @bitabar/api authz:matrix`. A test regenerates it in memory and fails on any
  difference. The BFLA test suite iterates the same data (route × role → expected status).
- **Z13 — Swagger is environment-gated (owner C1).** Swagger registration moves into a small
  testable helper (`src/swagger.ts` or equivalent) called by `main.ts` only when
  `nodeEnv !== 'production'`. A test boots the real module with production config and asserts
  `/api/docs` and `/api/docs-json` are `404`; development/test keep both. This is a code change in
  T03, not a T01 docs change.
