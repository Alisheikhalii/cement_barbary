## C. Architecture and security decisions

Owner-approved on 2026-11-18: **D1** app filter + PostgreSQL RLS, **D2** forward-only migrations + pre-deploy backup.
Already approved earlier: ORM = Drizzle (AGENT.md §3). Everything else below is an architect decision recorded in ADR-005 (task T01).

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                             | Reason                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| D1  | **Two layers of tenant isolation.** (1) App layer: tenant data is reachable only through `TenantDb.run()`, which requires a tenant context. (2) DB layer: Row-Level Security (RLS) on every tenant-owned table, with a policy that compares the row's tenant to `app.current_tenant_id()`.                                                                                                                                                           | A forgotten `WHERE` must not leak data (GUIDELINES §4, §6.2 IDOR).                                             |
| D2  | **Forward-only migrations.** Mistakes are fixed with a new migration. A DB backup runs before every production migration (F8 runbook). Migrations are never applied automatically on app start. They run through an explicit command or deploy step.                                                                                                                                                                                                 | Drizzle has no down migrations. Hand-written down scripts break silently over time.                            |
| D3  | Driver: `pg` (node-postgres) + `drizzle-orm/node-postgres`. Migrations: `drizzle-kit generate` (SQL committed to Git) + the `drizzle-orm` migrator.                                                                                                                                                                                                                                                                                                  | Most mature driver; works with Testcontainers.                                                                 |
| D4  | **Two DB roles.** The _migration owner_ (`DATABASE_MIGRATION_URL`; in dev the compose `POSTGRES_USER`) owns the schema. The _runtime role_ `bitabar_app` (`DATABASE_URL`) is `NOSUPERUSER NOBYPASSRLS NOCREATEROLE`, is not a table owner, and has DML grants only. A migration creates `bitabar_app` as `NOLOGIN` with no password. Each environment enables login with a password that never goes into Git (dev script, test harness, F8 runbook). | RLS does not apply to superusers or table owners. The app must never connect as one.                           |
| D5  | Tenant GUC: `app.tenant_id` (and `app.carrier_id`, reserved for F1-08), set **only** through `select set_config('app.tenant_id', $1, true)`, a parameterized, transaction-local call. Never use `SET LOCAL ... '${value}'` (SQL injection risk).                                                                                                                                                                                                     | Safe binding; the value resets automatically at commit or rollback, so pooled connections never leak a tenant. |
| D6  | **Fail closed.** `app.current_tenant_id()` returns `NULL` when the setting is missing. Policies then match zero rows, and `WITH CHECK` rejects inserts. In the app, `TenantDb.run()` without a context throws `TENANT_CONTEXT_MISSING` (HTTP 500, a programming error).                                                                                                                                                                              | A missing context never means "all tenants".                                                                   |
| D7  | IDs: UUID v7, generated in the app with the `uuid` package (`v7()`); column type `uuid`.                                                                                                                                                                                                                                                                                                                                                             | GUIDELINES §4. PostgreSQL 17 has no native `uuidv7()`. Time-ordered IDs keep indexes efficient.                |
| D8  | Standard columns: `id`, `tenant_id` (tenant-owned tables), `created_at`, `updated_at` (`timestamptz`, default `now()`, `updated_at` refreshed on update), `created_by uuid NULL` (FK to `users` added in F1-03), and `deleted_at timestamptz NULL` (operational tables only).                                                                                                                                                                        | GUIDELINES §4, PRD §6.                                                                                         |
| D9  | Every tenant-owned table gets: `tenant_id uuid NOT NULL REFERENCES tenants(id)`, an index whose leading column is `tenant_id`, `ENABLE ROW LEVEL SECURITY`, and the policy from the template in T04. Unique constraints are **per tenant** (`(tenant_id, code)`), partial on `deleted_at IS NULL` where soft delete applies.                                                                                                                         | Consistent and greppable. Later tasks copy the template.                                                       |
| D10 | `TenantDb.run(fn, opts?)` opens **one transaction** per call (default READ COMMITTED; `opts.isolationLevel` can override). A nested `run()` inside an active run **reuses** the outer transaction. Service code receives `tx` and never opens its own connection.                                                                                                                                                                                    | Clear transaction boundaries (GUIDELINES §4).                                                                  |
| D11 | Raw DB access (`pg`, `drizzle-orm/node-postgres`, the root `DB` token) is allowed only under `apps/api/src/db/**`. ESLint `no-restricted-imports` enforces this.                                                                                                                                                                                                                                                                                     | Nobody can bypass `TenantDb` by accident.                                                                      |
| D12 | Integration tests: `@testcontainers/postgresql` (`postgres:17-alpine`), files named `*.int.test.ts`, separate Vitest config, `pnpm test:int`. CI runs them in the `quality` job. Unit tests (`pnpm test`) stay Docker-free.                                                                                                                                                                                                                          | GUIDELINES §8. Fast unit loop.                                                                                 |
| D13 | Platform-level, cross-tenant operations (for example, `PLATFORM_ADMIN` creating a tenant) are **not** built in F1-02. In F1-02, `tenants` rows are inserted only by the migration owner (tests, and the future seed).                                                                                                                                                                                                                                | Avoids adding an RLS bypass before RBAC exists. See open question Q1.                                          |

**Out of scope for F1-02** (documented so the executor does not add it): users, roles, sessions, OTP, password hashing,
RBAC, audit triggers, idempotency, outbox, Redis client, seed data, carrier RLS policies, setting `tenantId` in logs
(needs the auth guard, F1-04), and the Dockerfile.

### T04 — RLS foundation migration (custom SQL) ⚠ Opus review required

1. **Objective:** Create the runtime role, the tenant-context function, the grants, and RLS on `tenants`.
2. **Files:** create `apps/api/drizzle/0001_rls_foundation.sql` via `drizzle-kit generate --custom --name=rls_foundation` (this keeps the journal consistent), then fill in its body. Create `docs/security/rls.md` (short: the template below plus "how to add RLS to a new table").
3. **DB changes (exact SQL, statements separated by `--> statement-breakpoint`):**
   ```sql
   -- Runtime role: no login here (password set per environment, never in Git).
   DO $$ BEGIN
     IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'bitabar_app') THEN
       CREATE ROLE bitabar_app NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;
     END IF;
   END $$;
   CREATE SCHEMA IF NOT EXISTS app;
   REVOKE ALL ON SCHEMA app FROM PUBLIC;
   -- Fail closed: NULL when unset/empty → policies match nothing.
   CREATE OR REPLACE FUNCTION app.current_tenant_id() RETURNS uuid
     LANGUAGE sql STABLE PARALLEL SAFE
     AS $$ SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid $$;
   CREATE OR REPLACE FUNCTION app.current_carrier_id() RETURNS uuid
     LANGUAGE sql STABLE PARALLEL SAFE
     AS $$ SELECT NULLIF(current_setting('app.carrier_id', true), '')::uuid $$;
   GRANT USAGE ON SCHEMA app TO bitabar_app;
   GRANT EXECUTE ON FUNCTION app.current_tenant_id(), app.current_carrier_id() TO bitabar_app;
   GRANT USAGE ON SCHEMA public TO bitabar_app;
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO bitabar_app;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO bitabar_app;
   ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO bitabar_app;
   -- Drizzle's migration journal must not be touched by the app.
   REVOKE ALL ON SCHEMA drizzle FROM bitabar_app;
   -- tenants: the app may only see/modify its own tenant row; no insert/delete from the app in F1-02.
   ALTER TABLE tenants ENABLE ROW LEVEL SECURITY;
   CREATE POLICY tenants_isolation ON tenants FOR SELECT TO bitabar_app USING (id = app.current_tenant_id());
   CREATE POLICY tenants_update ON tenants FOR UPDATE TO bitabar_app
     USING (id = app.current_tenant_id()) WITH CHECK (id = app.current_tenant_id());
   REVOKE INSERT, DELETE ON tenants FROM bitabar_app;
   ```
   **Template for every future tenant-owned table** (copied into `docs/security/rls.md` and ADR-005):
   ```sql
   ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;
   CREATE POLICY <t>_tenant_isolation ON <t> FOR ALL TO bitabar_app
     USING (tenant_id = app.current_tenant_id())
     WITH CHECK (tenant_id = app.current_tenant_id());
   ```
   `FORCE ROW LEVEL SECURITY` is intentionally **not** used: the owner role is for migrations only, and the app never connects as owner (D4).
   If `drizzle` schema does not exist yet when this migration runs, wrap the `REVOKE ... drizzle` line in `DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_namespace WHERE nspname='drizzle') THEN ... END IF; END $$;`.
4. **Endpoints:** none. 5. **Contracts:** the SQL function names above are a stable contract.

### T08 — Tenant context and `TenantDb.run()` ⚠ Opus implementation or review required

1. **Objective:** The single, enforced path to tenant data (D5, D6, D10).
2. **Files:**
   - Create `apps/api/src/db/tenant-context.ts`
   - Create `apps/api/src/db/tenant-db.ts`
   - Create `apps/api/src/db/tenant-context.test.ts`
   - Create `apps/api/test/tenant-db.int.test.ts`
   - Modify `apps/api/src/db/database.module.ts` (export `TenantDb` and `TenantContext`)
   - Modify `apps/api/src/common/errors/domain-error.ts` (add `static tenantContextMissing()`: code `TENANT_CONTEXT_MISSING`, status 500, generic Persian message `'خطای داخلی سرور رخ داد'`)
3. **Contracts:**

   ```ts
   // tenant-context.ts — AsyncLocalStorage-based, no NestJS request scope.
   export interface TenantScope {
     readonly tenantId: string;
     readonly carrierId?: string;
   } // both UUID
   export class TenantContext {
     run<T>(scope: TenantScope, fn: () => Promise<T>): Promise<T>; // validates UUIDs with zod (z.uuid()); throws DomainError.badInput on invalid
     current(): TenantScope | undefined;
     require(): TenantScope; // throws DomainError.tenantContextMissing()
   }
   // tenant-db.ts
   export type Tx = Parameters<Parameters<Db['transaction']>[0]>[0];
   export class TenantDb {
     run<T>(
       fn: (tx: Tx) => Promise<T>,
       opts?: { isolationLevel?: 'read committed' | 'repeatable read' | 'serializable' },
     ): Promise<T>;
   }
   ```

   `TenantDb.run` algorithm:
   1. `scope = context.require()`.
   2. If an ALS-stored active `tx` exists for this scope → `return fn(tx)` (nested reuse; the `isolationLevel` of the inner call is ignored, document this in JSDoc).
   3. Otherwise `db.transaction(async (tx) => {...}, { isolationLevel })`. Inside it:
      - `await tx.execute(sql\`select set_config('app.tenant_id', ${scope.tenantId}, true)\`)`
      - if `carrierId` is set, do the same for `app.carrier_id`
      - store `tx` in ALS and `return fn(tx)`

   A nested `TenantContext.run` with a **different** tenant while a transaction is active → throw `TENANT_CONTEXT_MISSING` (switching tenants inside a transaction is forbidden).

4. **DB changes:** none.
5. **Endpoints:** none. Wiring the context from the JWT is F1-04.
6. **Dependencies:** T07 (int tests need T04 and T06).
7. **Security:**
   - Parameterized `set_config` only.
   - Transaction-local (`true`), so pooled connections never keep a tenant.
   - Each scope is validated as a UUID before it reaches SQL.
   - No method accepts `tenantId` as a function argument from callers other than `TenantContext.run`.
8. **Unit tests (`tenant-context.test.ts`):**
   - `require()` outside `run` throws `TENANT_CONTEXT_MISSING`
   - `current()` inside `run` returns the scope
   - an invalid UUID → `BAD_INPUT`
   - context propagates across `await` and `Promise.all`
   - parallel runs with different tenants do not leak into each other (`Promise.all` of 50 runs, each asserting its own id)
9. **Integration (`tenant-db.int.test.ts`, runtime role):**
   - `run` without context → throws, and no query is sent
   - inside tenant A, `select app.current_tenant_id()` = A
   - after `run` completes, a fresh query on the same pool connection (`pool.max=1`) shows the setting is empty (no leak)
   - a nested `run` reuses the same transaction (same `txid_current()`)
   - an error inside `fn` rolls back
   - `isolationLevel: 'serializable'` is applied (`show transaction_isolation`)
10. **Acceptance:** all green; an Opus reviewer has checked the ALS and transaction logic and the no-leak test.
