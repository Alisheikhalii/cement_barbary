## B. Scope

**In scope (owner decision 2026-11-20):** one login method for all 3 roles in v1 — **password only**
(Argon2id, lockout, no default passwords), built behind a pluggable `CredentialMethod` interface so
`OtpMethod` can be added later without touching the login flow, token/session code or the tables that
matter (§J). Staff identify as `username@tenant-code`; drivers identify by **phone + password** (A4/A5).
Short-lived access token; rotating refresh token with reuse detection in an HttpOnly cookie; single
active session for drivers (BR-18); logout; `GET /auth/me`; first-password setup / forced change /
operator-assisted reset (A19, owner Q4); dev-seed credentials from env. New tables:
`user_credentials`, `auth_sessions`, `auth_rate_limits`.

**Out of scope** (the executor must not add these): **OTP login and everything SMS — `otp_challenges`,
`SmsProvider`, the dev SMS outbox — are designed, not built (§J)**; RBAC/permission guards, `can()`,
the permission matrix (F1-05); audit log, idempotency, outbox (F1-06); web UI (F1-09); self-service
"forgot password" (no delivery channel until SMS exists — operator-assisted reset only, A19); admin
unlock UI (lockout is time-based); national-ID writes (F4); carriers and `carrier_id` on users
(F1-08); any default or hardcoded password anywhere.

| A1  | **Passwords: Argon2id** via `@node-rs/argon2` (prebuilt native binaries, no node-gyp — important on this Windows/network setup), Parameters come from **env config, not magic constants** (owner condition 7): `AUTH_ARGON2_MEMORY_KIB` (default **19456** = 19 MiB), `AUTH_ARGON2_TIME` (default **2**), `AUTH_ARGON2_PARALLELISM` (default **1**) — the OWASP minimum is the documented **floor**, and Zod startup validation **rejects weaker-than-minimum settings** (m < 19 MiB, t < 2 or p < 1 fails startup; a test proves it). | A2  | **Progressive delay / soft lock instead of a long hard lock (owner condition 1).** On `user_credentials`: `failed_attempts int NOT NULL DEFAULT 0`, `next_attempt_at timestamptz NULL`. Each consecutive failure pushes `next_attempt_at` out by `AUTH_LOCK_BASE_SECONDS × 2^(failed_attempts-1)`, capped at `AUTH_LOCK_MAX_SECONDS` (env config, defaults **1 s base, 300 s cap** → 1 s, 2 s, 4 s … 5 min); counters reset on success. An account under delay gets the **same generic 401** as a wrong password — never a 429 and never a "locked" message (no enumeration, no oracle). Unlock is time-based only in v1. The per-IP and per-tenant-code buckets (A11) are the second layer, so an attacker who knows a driver's phone cannot keep that driver delayed for long.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | GUIDELINES §6.1 lockout; owner condition 1 — a hard 15-min lock would let anyone who knows a driver's phone lock that driver out. Revealing "delayed" would confirm the account exists. Numbers are config, not magic constants.                             |
| A3  | **No user enumeration (recorded hard rule):** every auth flow has exactly one generic failure — `401 {error:{code:"INVALID_CREDENTIALS"}}` for login and password change — with **identical status, body and headers** for: unknown user, malformed identifier, wrong password, locked account, disabled/deleted user. The unknown-user path runs a **dummy Argon2 verify** against a constant PHC hash to keep timing similar. Tests assert structural equality and that the dummy verify ran, **plus a timing-similarity test (owner condition 3):** over ≥ 20 samples per failure kind, the absolute difference of medians between any two failure paths must be **≤ max(50 ms, 20%)** — the tolerance is stated here so it can be re-tuned if CI hardware drifts; the test runs in the integration suite against real Argon2, in its own file without parallel workers, to keep noise down. The future OTP flow must follow the same rule (§J).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | AGENT.md §6 requirement; OWASP.                                                                                                                                                                                                                              |

Driver identifier is the **phone only**; resolution fans out server-side: the app caches `(id, code)` of tenants (60 s TTL, one forced refresh on miss) and computes the per-tenant blind-index hash (HMAC input includes tenant — unchanged from ADR-006 U8) for every tenant, then one DB round trip. OTP for drivers is designed, not built (§J).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Owner decision 2026-11-20: v1 is password-only for every role; the phone stays the driver identity (PRD). | A7  | **Access token (owner condition 8):** JWT HS256 via `jose` (pure JS, no native deps), `AUTH_TOKEN_SECRET` (env, base64 → 32 bytes), TTL **10 min** (`AUTH_ACCESS_TOKEN_TTL_SECONDS`, default 600), claims `sub`, `tid`, `sid`, `roles[]`, `jti`, `iat`, `exp` — **no PII in claims** (ids, role codes and token metadata only; a test asserts the exact claim set). Verify **pins the algorithm explicitly** (`jwtVerify(…, { algorithms: ['HS256'] })` — no alg switching; `none`, HS384 and RS256 tokens are rejected by test) and checks `iss`/`aud`/`exp`. Returned in the JSON body (client keeps it in memory). Alternative rejected: asymmetric keys (no second service exists in v1 to justify key distribution).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Short-lived bearer limits the blast radius of a leak; HS256 is sufficient for one issuer/verifier.                                                                                                                                                           |

The policy is role-aware: it is applied from the account's roles at set/change time; an account holding both kinds of role follows the staff rule.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Owner decision 2026-11-20. ## J. Future: OtpMethod (designed, not built)

Everything in this section is **specification for a later phase** — the executor must not write this
code in F1-04. It exists so the F1-04 design leaves the right seams.

- **Plug-in point:** `OtpMethod implements CredentialMethod` (A6) with `kind = 'otp'`, registered in
  `AuthModule` next to `PasswordMethod`. The controller gains `POST /auth/otp/request` and
  `POST /auth/otp/verify`; both delegate to the same method-agnostic session issuance, BR-18
  revocation, cookies and rate limiting. Token/session code and the F1-04 tables do not change.
- **New table:** `otp_challenges` (tenant-owned, RLS template verbatim, composite FK
  `(tenant_id, user_id) → users(tenant_id, id)`, index leading with `tenant_id`): `id` (app-side
  uuid), `tenant_id`, `user_id`, `code_hash bytea NOT NULL`, `expires_at`, `attempts int DEFAULT 0`,
  `consumed_at`, `superseded_at`, `requested_ip`, `created_at`. New env: `OTP_HMAC_KEY` (same
  validation and distinctness rules as the other secrets, A13).
- **New components:** `OtpService` (generate / hash / verify), `SmsProvider` interface +
  `MockSmsProvider` (in-memory outbox; the real Iranian provider plugs in at F8 by config, callers
  unchanged), and the dev-only `GET /dev/sms-outbox` (owner Q3 answer: registered only when
  `NODE_ENV=development` **and** bound to localhost; never logged or written to disk; a test proves
  it is absent in a production-configured app).
- **Security rules it must follow:** 6 digits from a crypto RNG (leading zeros allowed); 120 s
  expiry; max 5 attempts per challenge, then the challenge is dead; a new request supersedes the
  previous challenge; storage only as `HMAC-SHA256(OTP_HMAC_KEY, challenge_id + ":" + code)`,
  compared with `timingSafeEqual`; rate limits 1/60 s and 5/hour per phone + 30/hour per IP; request
  and verify responses are enumeration-safe exactly like A3 (identical for unknown phone,
  staff-role phone, expired or wrong code); the code never appears in logs, error messages, files or
  snapshots; driver session rules (BR-18, A10) apply unchanged.
- **Security checkpoint when built:** the password/OTP-code owner review from §G applies to the
  OtpMethod diff before its commit.
