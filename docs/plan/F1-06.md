### B.1 Owner approval conditions (2026-11-22, binding)

- **C1 — Idempotency handler time cap.** A config value (`IDEMPOTENCY_HANDLER_TIMEOUT_MS`, default **8000 ms**,
  bounds 1000–30000) caps how long a handler may hold the claim row and its locks. A timeout **rolls the outer
  transaction back**, so **no key row is stored** and a client retry with the same key **executes the handler
  again**; the client gets a generic `503 IDEMPOTENCY_TIMEOUT`. The default sits above the DB statement timeout
  (5000 ms) so ordinary DB slowness surfaces as its own error first.
- **C2 — `audit_logs` retention is debt, not code.** No purge in F1-06. Recorded in AGENT.md §7 with an **F8
  runbook item** (`docs/runbooks/audit-retention.md` in F8): owner-run purge with a retention period decided then.
- **C3 — Failure-outcome rows are best-effort.** ADR-009 states exactly what is guaranteed: a **success** audit row
  commits atomically with the change it describes; a **failure/denial** row is written after the rollback in its own
  transaction and may be lost only if the DB or process dies in that window (logged; the HTTP response is never
  changed). This is an accepted, documented limitation.
- **C4 — Migration approval.** Every migration (0011–0016) requires owner approval of its **exact SQL before it is
  written**; the SQL is shown at CP2 (0011/0012), CP4 (0013/0014) and CP5 (0015/0016). The definer catalog must
  stay exactly 6 functions.
- **C5 — Auth suites unchanged.** After T06, `auth-timing` and `auth-rate-limit` suites must pass **without any
  assertion or tolerance change**.
- **C6 — No new HTTP endpoint.** Probe routes are test-only and refused by the production boot scan. If an endpoint
  becomes necessary, STOP and ask.

## C. Decisions (L1–L14) — confirmed at CP1

### Audit

- **L1 — Two write paths, one table.** (a) `AuditWriter.append(entry)` runs inside the **caller's** `TenantDb.run`
  transaction (ALS reuse) → the audit row commits or rolls back with the business change (**fail-closed**).
  (b) The persistent `AuditHook` used by `SensitiveAuditInterceptor` opens `tenantContext.run({tenantId})` +
  **outer** `TenantDb.run` around the sensitive handler, so handler writes and the success row are one transaction.
  A failure row is written after rollback in a fresh transaction (C3).
- **L2 — Before/after via `AuditContext`.** Domain services call `auditChange({ resourceType, resourceId, before,
after })` (ALS slot); the interceptor/writer consumes it. Snapshots pass through `toAuditSnapshot(entity, row)`:
  **per-entity field allowlist**, unknown keys dropped (fail-closed); phone/national id become `maskPhone()` /
  `maskNationalId()` output; `*_enc`/`*_hash`/password/token/cookie keys are never allowed. jsonb size cap 16 KiB
  per column (DB CHECK).
- **L3 — Append-only enforced twice.** `bitabar_app` gets `SELECT, INSERT` only (explicit REVOKE UPDATE/DELETE/
  TRUNCATE — default privileges would grant them) **and** a `BEFORE UPDATE OR DELETE` row trigger +
  `BEFORE TRUNCATE` statement trigger (SECURITY INVOKER, pinned `search_path`, raises `42501 AUDIT_APPEND_ONLY`)
  that also blocks the owner. Post-condition check in the migration (0010 pattern). Retention purge = owner runbook
  in F8 (C2), not code.
- **L4 — Actor model.** `actor_type ∈ {user, system}`; `actor_user_id` with composite FK
  `(tenant_id, actor_user_id) → users(tenant_id, id)`; `actor_session_id` (no FK). CLI/seed writes are `system`
  with a stable `metadata.tool`.
- **L5 — Auth events (timing-safe).** Written **inside existing auth transactions**, only on paths that already
  write and are never timing-compared with the unknown-user path: `auth.login.success` (metadata `method` and
  `prior_failed_attempts` read before reset — this is how a delay/lockout episode becomes visible), `auth.logout`,
  `auth.session.revoked_new_device` (BR-18), `auth.refresh.reuse_detected` (family-revocation tx),
  `auth.password.changed`, `auth.password.reset` (CLI), `user.role.assigned`, `user.role.revoked`. **Failed logins
  and delay hits are NOT rows** (Q1): they go to the structured security log (reason code, HMAC identifier from
  `rateLimitKeys`, IP, reqId). The `auth-timing` test stays unchanged (C5).
- **L6 — Denials and status.** An authenticated `403` on a **sensitive** permission → `outcome = denied` row (own
  transaction, best-effort, from the guard; non-sensitive 403s stay log-only). Every row stores the final
  `http_status` read from the response at finalize (closes the T06 outcome-vs-status note).
- **L7 — Free text.** `reason` stored as validated by `sensitiveReasonSchema`; it is user text and documented as
  such; never logged by pino (existing redaction).

### Idempotency

- **L8 — One-transaction claim.** `@Idempotent()` interceptor, inside one `tenantContext.run` + outer `TenantDb.run`:
  `SET LOCAL lock_timeout = :lockTimeout` → `INSERT … ON CONFLICT DO NOTHING` claim row → handler (its repositories
  reuse the same transaction through ALS) → `UPDATE` the row to `completed` with status + encrypted response →
  commit. A concurrent duplicate blocks on the unique key and, after the first commits, sees `completed` →
  **replay**; if the lock wait times out → `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1`. A handler error →
  rollback → **no row** (retry re-executes; nothing changed). A crash mid-handler leaves no row either — the claim
  was never committed, so no stale `in_progress` row can exist. **Handler cap (C1):**
  `IDEMPOTENCY_HANDLER_TIMEOUT_MS` (default 8000) — on timeout the transaction is aborted (PG `statement_timeout`
  for the handler's queries plus a JS guard), the key is not stored, and the client receives a generic
  `503 IDEMPOTENCY_TIMEOUT` (Persian message, no details) and may retry with the same key.
- **L9 — Key semantics.**
  - Header `Idempotency-Key`, pattern `^[A-Za-z0-9_-]{16,128}$`; missing or malformed on an `@Idempotent` route →
    `400 IDEMPOTENCY_KEY_REQUIRED` with a generic body. The key is opaque: never logged, never stored in plaintext
    form beyond the column that is tenant+user+route scoped (it is not PII and is not encrypted; the response is).
  - Scope is the tuple `(tenant_id, user_id, route_key, idem_key)` where `route_key = METHOD + " " + route
template` (e.g. `POST /api/v1/base/destinations`), **not** the raw URL — query strings never split a scope.
  - Fingerprint = SHA-256 over a **canonical JSON** of `{params, query, body}`: object keys sorted recursively,
    arrays keep order, `undefined` omitted, numbers normalized, strings as-is; stored as `bytea(32)`.
  - Same key + same fingerprint + `completed` → **replay**: stored status and body are returned, plus header
    `Idempotent-Replayed: true`. Stored headers are deliberately not replayed; only status + JSON body.
  - Same key + **different** fingerprint → `422 IDEMPOTENCY_KEY_REUSED` (generic message; no diff detail).
  - Same key + `in_progress` (a live concurrent request) → wait up to `IDEMPOTENCY_LOCK_TIMEOUT_MS` (default
    2000, bounds 100–10000); then `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1`.
  - Expired row (`expires_at < now()`, 24 h via `IDEMPOTENCY_TTL_HOURS`, DB clock) → CAS `UPDATE … WHERE
expires_at < now()` resets it to `in_progress` with the new fingerprint and the handler runs as a new request.
  - The route key, tenant and user always come from the server (route metadata, principal) — never from the
    request.
- **L10 — Coverage rule.** Boot scan + route-scan test: every `@RequirePermission` production route with
  POST/PUT/PATCH/DELETE must carry `@Idempotent()`; the opt-out allowlist is empty. `@Public` auth routes are
  exempt (their own rotation/CAS logic), `@SelfService` GETs are exempt (non-mutating).
- **L11 — Storage hygiene.** `response_enc` via `PiiService` (AES-GCM, AAD
  `tenant:idempotency_keys.response_enc:<rowId>`), cap 64 KiB (larger → generic 500, logged); `response_status`
  smallint. Cleanup: runtime job per tenant deletes expired rows; DELETE is allowed only through a RESTRICTIVE
  policy `expires_at < now()`, so even our own role cannot delete a live key.
- **L12 — Outbox producer.** `OutboxWriter.enqueue({ topic, dedupeKey, payload })` inside the business transaction;
  `payload_enc` encrypted (payload may carry a phone); unique `(tenant_id, topic, dedupe_key)` → duplicate enqueue
  is a no-op. `topic` matches `^[a-z][a-z0-9_.]{2,63}$`.
- **L13 — Worker: Postgres poller (Q3).** In-process Nest module behind `OUTBOX_WORKER_ENABLED` (off by default in
  test and production until F8). Tick: for each active tenant (`app.list_tenants`, existing) → `TenantDb.run`:
  `SELECT … WHERE (status = 'pending' AND next_attempt_at <= now()) OR (status = 'processing' AND locked_until <
now()) ORDER BY next_attempt_at FOR UPDATE SKIP LOCKED LIMIT n` → mark `processing` + `lock_token` +
  `locked_until` + `attempts + 1` → commit → call the adapter **outside** any transaction with a timeout → CAS on
  `(id, lock_token)` to `sent`, or to `pending` with exponential backoff + jitter, `dead` after `max_attempts`.
  `last_error_code` is a sanitized stable code, never provider text. **No new SECURITY DEFINER function.**
- **L14 — No duplicate side effects.** Delivery is at-least-once; the adapter receives `outbox.id` as its
  idempotency key. `MockAdapter` (topic `mock.echo`, flag `ADAPTER_MOCK_ENABLED`) dedupes by that id; a test kills
  the worker between send and mark and proves exactly one effect.

### Debts

- **D1 — `@SelfService` allowlist (MEDIUM-2).** `SELF_SERVICE_ROUTE_ALLOWLIST = [GET /api/v1/auth/me]` in
  `route-scan.ts`, enforced by boot + scan test, with a negative control (a throwaway self-service route fails
  both).
- **D2 — assign/revoke oracle.** New `UserRoleService` (no HTTP) — the only caller of `assignRole` / `revokeRole`.
  Nonexistent, other-tenant and soft-deleted users all produce an **identical** `DomainError.notFound()` for
  **both** operations (repository maps `P0002 → notFound`; revoke verifies user visibility in the same
  transaction); a visible user returns `{ changed: boolean }`. Writes `user.role.assigned/revoked` audit with
  before/after role sets. The operator CLI switches to it. Justified by L5.
- **D3 — 5xx sanitization.** `sanitizeErrorForLog(e)` → `{ name, sqlState?, constraint?, errorCode, stack frames
without message }`; for non-`DomainError` the `message`, `detail`, `query`, `params`, `cause` values are dropped.
  Used by the global filter, the audit-hook failure log and the outbox worker.
