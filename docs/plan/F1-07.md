## Context

F1-06 built audit, idempotency and outbox but no business endpoint exists. PRD §5.2 needs operator-managed base
data before load announcements (F2) and the queue engine (F3): destinations (one queue per destination, PRD §3,
BR-01), halls with terminals (§3 "Hall"), and loader types as **data, not an enum**, with grouping (BR-06 matches
driver vehicle to announcement loader type/group, incl. a "second loader group"). These are the **first real
endpoints**, so they prove every F1-05/F1-06 contract end-to-end: `@RequirePermission`, `@Idempotent`, audit
before/after, strict Zod + mass-assignment scan, soft delete, pagination, RLS + U14, matrix.

## C. Decisions (B1–B12) — confirmed at CP1

### API shape

- **B1 — REST under `/api/v1/base/*`** (matches the ADR-010 example route key). Single path per handler.

  | Resource           | Routes                                                                                         | Permission                    |
  | ------------------ | ---------------------------------------------------------------------------------------------- | ----------------------------- |
  | Destinations       | `GET/POST /base/destinations`, `GET/PATCH/DELETE /base/destinations/:id`                       | `destination.read` / `.write` |
  | Halls              | `GET/POST /base/halls`, `GET/PATCH/DELETE /base/halls/:id`                                     | `hall.read` / `.write`        |
  | Terminals          | `GET/POST /base/halls/:hallId/terminals`, `GET/PATCH/DELETE /base/halls/:hallId/terminals/:id` | `hall.read` / `.write`        |
  | Loader-type groups | `GET/POST /base/loader-type-groups`, `GET/PATCH/DELETE /base/loader-type-groups/:id`           | `loader_type.read` / `.write` |
  | Loader types       | `GET/POST /base/loader-types`, `GET/PATCH/DELETE /base/loader-types/:id`                       | `loader_type.read` / `.write` |

  25 routes. `POST` → 201 `{data}`; `PATCH` → 200 `{data}`; `DELETE` → 204. Every POST/PATCH/DELETE has
  `@Idempotent()`. No permission is added or changed.

- **B2 — Fields** (all `.strict()` Zod; ids are UUID params):
  - destination: `name` (2–64), `provinceName` (0–64, optional), `isActive` (default true), `displayOrder` (int
    0–9999, default 0).
  - hall: `name`, `isActive`, `displayOrder`. terminal: `name`, `isActive`, `displayOrder` (hall from path only,
    verified in scope).
  - loader-type group: `name`, `isActive`, `displayOrder`. loader type: `name`, `groupId` (uuid, required),
    `isActive`, `displayOrder`.
  - Server-only: `id`, `tenant_id`, `name_key`, `version`, `created_at/updated_at/deleted_at`. Never accepted.
- **B3 — Pagination & listing.** `@ZodQuery` strict: `page` ≥1 (default 1), `pageSize` 1–100 (**default 50**),
  `isActive` (bool, optional), `q` (name substring on `name_key`, 1–64, LIKE-escaped), `sort` ∈ allowlist
  (`displayOrder`, `name`, `createdAt`, each `-` for desc; default `displayOrder,name`; id as final tiebreak).
  Response `{data: [...], meta: {page, pageSize, total}}`. `q` has no trigram index — acceptable at current
  volumes, known limit in ADR-011 (R4). Soft-deleted rows never listed. Loader types also filter
  by `groupId`.

### Integrity

- **B4 — Uniqueness per tenant, live rows only.** `name_key` = server normalization of `name` (NFC, trim, collapse
  whitespace, ZWNJ→space, Arabic ي/ك→Persian ی/ک, Persian/Arabic digits→ASCII, lowercase). Partial UNIQUE indexes
  `WHERE deleted_at IS NULL`: destinations `(tenant_id, name_key)`; halls `(tenant_id, name_key)`; terminals
  `(tenant_id, hall_id, name_key)`; groups `(tenant_id, name_key)`; loader types `(tenant_id, name_key)` (not per
  group: a type name means one vehicle class). A soft-deleted name is reusable. `23505` → `409 CONFLICT` with
  generic body + `details.field = "name"` (4xx details allowed). ❓Q1.
- **B5 — Delete = soft delete, blocked when in use.** `DELETE` sets `deleted_at`; a row referenced by a **live**
  child answers `409 IN_USE` (generic, no child ids): hall with live terminals, group with live loader types. The
  check runs in the same transaction with the parent row locked `FOR UPDATE` (no race with a concurrent child
  insert, which also locks the parent). A `ReferenceGuard` registry (per entity, in-tx check functions) lets F2/F3
  add "referenced by announcement/queue" checks without changing these services. Deactivation (`isActive=false`)
  is the normal operator path. Creating a child under an inactive parent is allowed; under a deleted parent is 404.
  `ReferenceGuard` is minimal (R3): one interface `{ isReferenced(tx, scope, id): Promise<boolean> }`, one check
  each for hall and group, one unit test.
- **B6 — Optimistic concurrency.** Every row has `version int`; `PATCH`/`DELETE` body/query carries
  `expectedVersion`; mismatch → `409 STALE_VERSION`. Prevents two operators silently overwriting each other.
  `DELETE` takes it in the query (`?expectedVersion=n`): part of the idempotency fingerprint, an integer with no
  sensitive data (R5).
- **B7 — Scope/IDOR.** Repositories accept only `AccessScope`; every query `tenant_id AND id` (terminals also
  `hall_id`). Other tenant / deleted / nonexistent → identical 404. Composite FKs `(tenant_id, hall_id) →
halls(tenant_id, id)` and `(tenant_id, group_id) → loader_type_groups(tenant_id, id)` make a cross-tenant parent
  impossible at the DB. A body `groupId` that is another tenant's, deleted or nonexistent → the identical generic
  `404` (no existence oracle).

### Audit, idempotency, security

- **B8 — Audit.** Each write: `auditChange({resourceType, resourceId, before, after})` + `AuditWriter.append` in
  the service transaction (atomic, fail-closed). Actions: `<entity>.created|updated|deleted` (e.g.
  `destination.updated`, `terminal.deleted`, `loader_type_group.created`). Snapshot allowlist entries for the 5
  entities = business fields + `version` + `deleted_at` (no `name_key` needed; no PII exists). `metadata` only
  `{hallId}` / `{groupId}` (structural uuids). Non-sensitive → no `reason`. Replay writes no row (F1-06).
- **B9 — Idempotency.** `@Idempotent()` on all 15 mutating routes; responses are small (<64 KiB). Effects only
  inside the request tx (no outbox needed yet).
- **B10 — DB rules.** RLS template on all 5; `DELETE`/`TRUNCATE` revoked from `bitabar_app` (soft delete only);
  CHECKs: name length, `display_order BETWEEN 0 AND 9999`, `version >= 1`, `name_key <> ''`. Migration post-
  conditions fail closed (0016 pattern: `BASE_RLS_INVALID` / `BASE_POLICY_INVALID` / `BASE_GRANTS_INVALID`).
- **B11 — Boundaries.** `src/modules/base-data/{destinations,halls,loader-types}/` (controller/service/
  repository/schemas); shared helpers `src/common/pagination/` and `src/common/text/name-key.ts`. New controllers
  added to `PRODUCTION_CONTROLLERS` and the `authz:matrix` script; matrix regenerated per task.
- **B12 — Operator UI split (decision, no UI now).** F1-09 = web skeleton + login + operator shell; base-data pages
  follow in a separate F1-09 sub-task: **3 pages** matching PRD routes — `/destinations` (table + drawer form +
  active toggle), `/halls` (table; terminals edited in the hall detail drawer), `/loader-types` (two tabs: groups,
  types). Default columns + column chooser (CLAUDE.md §5). Confirmed again at F1-09 start (AGENT.md §6).

## D. T01 — the two repeat flakes (decision: **fix at root in T01, timeboxed**; ❓Q3)

Rule: no assertion/tolerance loosened; if the root cause is test-harness only, fix the harness; if production, fix
code. Timebox: one investigation pass (read-only subagent: targeted logs/SQLSTATE capture, hypotheses) + one fix.
If unresolved → defer to F7 with the evidence recorded.

- **F-A `auth-rate-limit` 50-way upsert (`57014`).** Hypothesis 1 (production defect, check first): the bucket row
  lock is held for the whole login transaction (including Argon2 verify), so 50 requests serialize at ~100 ms each
  → >5 s. Fix: upsert the counter in its own short statement/transaction before credential work (commit order
  preserved, same bucket semantics). Hypothesis 2 (harness): CPU starvation only → run that file in a dedicated
  vitest project/pool with its own container.
- **F-B `auth.e2e` two parallel password changes (expected `[200,401]`).** Hypothesis: the loser gets a transient
  5xx (deadlock `40P01` / lock contention) instead of the CAS 401. Fix: capture the actual status + SQLSTATE; if a
  DB error surfaces as 500, lock order fix (user row first — the T06 pattern) or map the specific SQLSTATE to the
  same generic 401. A concurrent change must never be a 500.
- Proof (R2): each targeted file 50× green; full `test:int` a few times locally with `maxWorkers: 1` (as many as
  memory allows, stopped runs reported); CI is the independent run.

  list default 50 / max 100 / `pageSize=101` 400 / sort allowlist / `q` LIKE-escape (`%`, `_`); unknown key and

  ي/ی, ZWNJ, digit, case variants) 409; reuse after soft delete OK; stale version 409; deleted → 404 on
  GET/PATCH/DELETE; in-use delete 409; idempotent replay (same status/body, `Idempotent-Replayed`, one audit row,
  one side effect), different payload 422, missing key 400.
- **Isolation:** tenant B cannot read/patch/delete tenant A rows (404 identical to nonexistent); terminal of hall A
  via hall B path → 404; `groupId` of tenant B → 404; DB: RLS probes, forged `tenant_id` 42501 WITH CHECK,
  composite FK rejects cross-tenant parent, `bitabar_app` DELETE/TRUNCATE 42501, U14 guard green.
- **Audit:** created/updated/deleted rows with correct before/after/actor/version; rolled-back write → no row; PII
  sweep unchanged.
- **Concurrency:** parallel delete-hall vs create-terminal → never a live terminal under a deleted hall; 20
  parallel creates of the same name → exactly one 201.
