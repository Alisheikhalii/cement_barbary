## ۶. فاز F7 – ایجنت امنیت (الزامی، بعد از اتمام ویژگی‌ها)

وقتی F6 تمام شد، نقش **Security Engineer مستقل** را بگیر. خروجی: `docs/reports/security-report-<تاریخ>.md` + خلاصه ساده برای مالک. هر یافته: شدت (Critical/High/Medium/Low)، شرح ساده، اثبات (PoC/تست)، راه‌حل، وضعیت (باز/رفع‌شده + Commit).

### ۶.۱ Authentication
- [ ] OTP: انقضا، محدودیت تلاش، Rate Limit، عدم افشای Brute-force، عدم Enumeration حساب
- [ ] رمزها Argon2id، سیاست رمز، قفل موقت، بازیابی رمز امن
- [ ] JWT/Refresh: انقضا، امضا (alg none/تغییر الگوریتم)، Reuse Detection، ابطال هنگام خروج/تغییر رمز
- [ ] Cookie: HttpOnly/Secure/SameSite؛ Session Fixation
- [ ] یک نشست/یک دستگاه برای راننده (BR-18) واقعاً اعمال می‌شود
- [ ] Credential Stuffing و OTP Bombing (SMS Pumping) مهار شده

### ۶.۲ Authorization
- [ ] **ماتریس دسترسی**: برای هر Endpoint × هر نقش تست خودکار (مجاز/ممنوع)
- [ ] Endpoint بدون Guard وجود ندارد (اسکریپت اسکن مسیرها)
- [ ] **IDOR/BOLA:** تغییر ID در همه منابع (اعلام بار، مجوز، کیف پول، تیکت، سند)؛ باربری A ↔ B، راننده ↔ راننده، Tenant ↔ Tenant
- [ ] **BFLA:** راننده/باربری به Endpointهای اپراتور دسترسی ندارد
- [ ] Mass Assignment (تغییر `role`, `tenantId`, `balance` از بدنه درخواست)
- [ ] ارتقای سطح دسترسی (Privilege Escalation) و دور زدن تایید لغو (BR-16)

### ۶.۳ سایر
- [ ] OWASP Top 10 + ASVS L2 چک‌لیست؛ Injection (SQL/NoSQL/Command)، XSS (Stored/Reflected)، CSRF، SSRF، Open Redirect، Path Traversal
- [ ] آپلود فایل، هدرهای امنیتی، CORS، CSP، Rate Limit
- [ ] **منطق مالی:** Double-spend/Race روی کیف پول، تکرار Callback درگاه، دستکاری مبلغ، Idempotency
- [ ] **منطق نوبت‌دهی:** دوبار تخصیص، پرش از صف، دستکاری زمان، ثبت هم‌زمان چندحسابی، دور زدن فیلتر نوع بارگیر
- [ ] وابستگی‌ها (`pnpm audit`)، Secret در Git/تاریخچه (gitleaks)، Docker Image (Trivy)
- [ ] زیرساخت: پورت‌های باز، دسترسی مستقیم DB/Redis، TLS، پیکربندی Nginx، Backup/Restore
- [ ] لاگ و Audit: ثبت رخدادهای حساس، عدم نشت داده در لاگ
- [ ] ابزارها: OWASP ZAP (Baseline+Active روی محیط تست)، Semgrep/CodeQL (SAST)، Trivy، gitleaks، تست‌های دستی/اسکریپتی برای منطق.

### ۶.۴ معیار قبول/رد امنیت
- **رد:** هر یافته Critical/High باز، یا شکست در تست IDOR/AuthZ، یا شکست تست مالی/نوبت.
- **قبول:** صفر Critical/High باز؛ Medium با برنامه رفع مکتوب؛ همه تست‌های ماتریس دسترسی سبز.
- اگر رد شد: **خودت اصلاح کن**، دوباره تست کن و تا قبول‌شدن تکرار کن؛ همه دورها را در گزارش بنویس.

## ۷. فاز F7 – بنچمارک و تست بار (الزامی)

محیط: **Staging شبیه Production** (همان مشخصات سرور، دیتابیس با داده Seed بزرگ). **هرگز روی Production واقعی تست بار نزن.** ابزار: **k6** (+ Playwright برای مرورگر، `pg_stat_statements` برای کوئری‌ها، Prometheus برای متریک).

Seed داده تست: ۱۰ مقصد، ۵۰ باربری، ۵٬۰۰۰ راننده، ۱۰۰٬۰۰۰ رکورد نوبت/تاریخچه، ۲٬۰۰۰ اعلام بار.

### ۷.۱ سناریوهای الزامی

| # | سناریو | بار هدف | معیار قبول |
|---|---|---|---|
| L1 | **ورود هم‌زمان رانندگان** (OTP Mock) | ۱۰۰۰ کاربر در ۶۰ ثانیه | خطا < ۱٪، p95 < ۸۰۰ms |
| L2 | مرور بارها/صف + فیلتر | ۱۰۰۰ کاربر هم‌زمان، ۱۰ دقیقه | p95 < ۳۰۰ms، خطا < ۰٫۵٪ |
| L3 | **ثبت نوبت هم‌زمان** (لحظه بازشدن) | ۱۰۰۰ درخواست در ۱۰ ثانیه | p95 < ۵۰۰ms، صفر تخصیص تکراری، ترتیب درست |
| L4 | **رزرو زمانی ۳ اولویتی** + Job تخصیص | ۵۰۰ راننده، ۶۰ بار | تخصیص < ۱۰ ثانیه، صفر Overbooking، نتیجه Deterministic |
| L5 | رقابت روی یک بار | ۲۰۰ درخواست هم‌زمان برای ۱ بار | دقیقاً ۱ برنده |
| L6 | کیف پول: شارژ + کسر هم‌زمان | ۵۰۰ عملیات روی ۵۰ کیف | موجودی نهایی دقیق، صفر دوبار کسر (تکرار Callback هم) |
| L7 | ثبت اعلام بار و گزارش‌های سنگین | ۵۰ باربری هم‌زمان، جدول ۱۰۰K ردیف | p95 < ۹۰۰ms، بدون Timeout |
| L8 | Realtime صف | ۱۰۰۰ اتصال WebSocket | تأخیر پخش < ۲ ثانیه، حافظه پایدار |
| L9 | Mixed Workload واقعی | ۱۵۰۰ کاربر، ۳۰ دقیقه | خطا < ۱٪، CPU < ۷۵٪، بدون افزایش حافظه |
| L10 | **Spike** | ۱۰۰ → ۲۰۰۰ کاربر ناگهانی | بدون Crash، بازیابی < ۲ دقیقه |
| L11 | **Soak** | ۳۰۰ کاربر، ۴ ساعت | بدون Memory Leak/افت کارایی |
| L12 | **Stress** (افزایش تا نقطه شکست) | تا ۵۰۰۰ | نقطه شکست و گلوگاه گزارش شود؛ تخریب تدریجی و بدون خرابی داده |
| L13 | **Chaos/بازیابی** | قطع Redis/DB/Restart API وسط بار | بدون خرابی داده، بازیابی خودکار، Jobها تکرار ناامن ندارند |
| L14 | Rate-limit و حمله | OTP Bombing، Brute-force ورود | مسدودسازی کارآمد، سرویس برای کاربران عادی سالم |

### ۷.۲ سایر بنچمارک‌ها
- **فرانت:** Lighthouse (موبایل، شبکه کند 3G/Fast 3G): Performance ≥ ۸۰، LCP < ۳s، حجم JS اولیه راننده < ۲۰۰KB gzip؛ PWA نصب‌پذیر؛ تست روی دستگاه ضعیف (CPU Throttle ×4).
- **دیتابیس:** بررسی کوئری‌های کند (> ۱۰۰ms)، Explain Analyze روی کوئری‌های صف، نبود N+1، ایندکس‌های لازم، Lock Wait.
- **زیرساخت:** مصرف CPU/RAM/Disk/Network، تنظیم Connection Pool، زمان Build/Deploy، زمان Backup و **تست بازیابی (RTO ≤ ۳۰ دقیقه، RPO ≤ ۲۴ ساعت)**.
- **صحت:** تست‌های Invariant بعد از هر سناریو (ظرفیت ≥ تخصیص، یکتایی، مجموع Ledger = موجودی).

### ۷.۳ خروجی
`docs/reports/benchmark-report-<تاریخ>.md` شامل: محیط تست، نمودار/جدول (RPS، p50/p95/p99، خطا، CPU/RAM)، گلوگاه‌ها، تغییرات اصلاحی، نتیجه **قبول/رد برای هر سناریو** و علت، و جمع‌بندی ساده برای مالک (مثلاً «سیستم تا N راننده هم‌زمان بدون مشکل کار می‌کند؛ در N+ مشکل X رخ می‌دهد؛ برای رفعش Y کردیم»).

**اگر رد شد:** علت ریشه‌ای را پیدا کن (پروفایل، Explain، لاگ)، اصلاح کن، دوباره تست کن؛ تا قبول‌شدن حلقه را تکرار کن و **هر دور را مستند کن** (قبل/بعد). فقط اگر محدودیت سخت‌افزار سرور مانع بود، به مالک بگو چه ارتقایی لازم است و چرا.
